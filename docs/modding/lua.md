# Lua scripts

The game logic is mostly native code. Lua is used for start-up configuration, the menu framework, goals and rewards, the on-screen display and the automatic tests. There are 102 compiled scripts in `scripts/`.

| Area | Scripts |
|---|---|
| Boot scripts (`scripts/bootscripts`) | Choose the start state machine and set engine options with `BootOptions.Set`, `RenderOptions.Set`, `GUIOptions.Set`, `Plugins.LoadPlugin` and others. |
| `scripts/lua/gameconfig` | Game configuration values. |
| `scripts/lua/libraries/rewards`, `driveractions`, `drift`, `crazyspeed` | Fame and reward rules, driver action scoring, drift scoring. |
| `scripts/lua/libraries/socialgoals*` | Social goals and challenges. |
| `scripts/lua/libraries/osd`, `scripts/lua/mvc/*` | The on-screen display and the model/view framework of the menus. |
| `scripts/lua/weatherpresetlookup` | Weather presets. |
| `scripts/autotest/lua` | Scripts that drive the game automatically (start a race, switch to AI, change the camera). |

[lua-names.md](lua-names.md) lists the globals, calls and table keys the scripts use, with the scripts that use them. It is generated by `dcmod lua survey`.

## Reading a script

```bash
dcmod lua dis @scripts/lua/libraries/rewards.lua.bin
```

Each line has the instruction, the source line and the constant it refers to, for example `GETGLOBAL ... ; "Rewards"`.

## Changing a script

- **A value**: `lua.const` replaces a number or string constant, in the whole script or one function. It needs no Lua source, and it keeps the rest of the script exactly.
- **A whole script**: compile your Lua source with `dcmod lua compile` and put the bytecode in `files/scripts/...` at the same path. The game runs bytecode but crashes on Lua source it has to compile itself, so do not ship the source text under the game's script names. The compiled script can be decompiled with a tool such as unluac, which is not part of this kit.

## Scripts that run at start-up

A mod can list Lua files, supplied in its `files` folder, under `"scripts"`:

```json
{ "id": "me.hello", "scripts": [ "scripts/mods/hello/main.lua" ] }
```

When any mod lists scripts, the build replaces the game's boot scripts (`scripts/bootscripts/defaultbootscript.lua.bin` and `releasebootscript.lua.bin`, the two names the game's executable refers to) with a short Lua text. It runs the original boot script, kept beside it as `..._dcmod_original.lua.bin`, and then each mod script in load order, each in its own `pcall`, so a script that fails does not stop the others.

**Scripts are compiled when the mod is built.** The game runs Lua bytecode but crashes when it runs a chunk it has compiled from text itself (`loadfile` or `loadstring` of source), so the kit compiles each source script with the real Lua 5.1.5 compiler (included in the kit, MIT licence) and the boot script loads the compiled file. `dcmod lua compile file.lua` does the same by hand. A mod may also list a script that is already bytecode. Do not call `loadstring` or `loadfile` on source text in a mod script.

### Logging

The game's `print` does not write to the log. The boot script defines `dcmod.log(...)`, which does:

```lua
dcmod.log("lap time", t)      -- the log gets:  Mod: lap time 83.2
```

It works by opening a path that the runtime recognises (`dcmod/log/<text>`); capital letters are sent as `^` and the letter because the game lower-cases paths, and characters other than letters, digits and `" .:=_,-()[]"` become `?`. Up to 20000 lines are written per run. This needs the runtime of this release or later.

### The dcmod library

Every mod script can use these (all of them run the function you give inside a `pcall`, and a failure is logged as `Mod: error in ...` without stopping anything else):

| Function | Does |
|---|---|
| `dcmod.log(...)` | Writes a line to the game log. |
| `dcmod.after(seconds, fn)` | Runs `fn` once, in real time. |
| `dcmod.every(seconds, fn)` | Runs `fn` again and again. This is a mod's update loop. |
| `dcmod.on_ready(fn)` | Runs `fn` once the game is up: `dcmod.ready_delay` seconds (20) after the start. The game's event system does not exist before that, and using it earlier crashes the game. |
| `dcmod.setting(mod, name, fallback)` | The value of a setting the mod offers (see [mod-format.md](mod-format.md)); `dcmod.settings[mod]` holds all of them. |
| `dcmod.on(event, fn)` | Calls `fn(...)` whenever the game sends the event (after the game is up). `NewLap`, `GUIPushPage` and `GUIPopPage` are events the game's own scripts listen for; the others it sends are in [lua-api.md](lua-api.md). |

```lua
dcmod.on("NewLap", function(...) dcmod.log("lap", ...) end)
dcmod.every(10, function() dcmod.log("still running") end)
```

Timers, the boot hook, `dcmod.on` and `dcmod.log` have been run in the game. The arguments an event passes are not documented anywhere; log them to see.

### The car the player drives: `dcmod.car()`

`dcmod.car()` returns a table with the live state of the car the player is driving, or `nil` when no car is driven (in the menus, loading a race):

| Field | Meaning |
|---|---|
| `speed`, `kmh` | Speed in m/s and in km/h. |
| `rpm`, `max_rpm`, `limiter` | Engine speed, the highest engine speed and the rev limiter. |
| `gear` | 1 and up forward, -1 reverse. |
| `throttle`, `brake`, `steer` | What the controller gives: 0 to 1, 0 to 1, -1 to 1 (steering wheels are not read yet). |
| `wheels[1..4]` | Right front, left front, right rear, left rear: `load`, `lateral`, `longitudinal` (forces in N), `slip_ratio`, `slip_angle`. |

```lua
dcmod.every(1, function()
  local car = dcmod.car()
  if car then dcmod.log(math.floor(car.kmh), "km/h,", math.floor(car.rpm), "rpm, gear", car.gear) end
end)
```

Windows only: on Linux `dcmod.car()` always returns `nil` (the car hook is not built there). The controller values are the pad's: with the AI driving they are 0 unless the pad is used; with `BB_PAD_FILE` holding `l2 lx=40` they read `brake` 1 and `steer` -0.69, which is (40 - 128) / 127.

Checked in the game (Ferrari 458 on Chile, 50 seconds of AI driving): speed went from 106 to 226 km/h, the gear from 3 to 6, and the front wheel load from 0 N in the air to 6800 N in a braking zone. The car is read through the same code as the telemetry output; the runtime installs it when a mods folder has scripts (the log says `a mod has scripts: the car state is available to them`).

How it works, for people who extend it: `dcmod.car()` calls `loadfile("dcmod/state/car.lua.bin")`. The runtime sees the path (`src/runtime_modapi.c`), writes a small Lua 5.1 chunk that returns the numbers into the user data folder and opens that file. The name must end in `.lua.bin`: the game's `loadfile` stops the game with an assertion for a path without it.

### Drawing on the screen: `dcmod.ui`

A script can draw text and filled rectangles over the game (the same layer as the FPS counter, so they also show over the menus). Positions and sizes are fractions of the screen, `size` is the height of the text in pixels, a colour is `{r, g, b, a}` with values from 0 to 1, and `ttl` is how many seconds an item stays when it is not drawn again (1 by default). An item with the same `id` is replaced, so a script that draws every 0.1 seconds with a `ttl` of 0.5 shows a live value and loses it when the script stops.

| Call | Does |
|---|---|
| `dcmod.ui.text(id, x, y, text, size, color, ttl)` | Text at (x, y), at most about 100 characters; any character works. |
| `dcmod.ui.rect(id, x, y, w, h, color, ttl)` | A filled rectangle of w by h. |
| `dcmod.ui.image(id, name, x, y, w, h [, tint, ttl])` | The picture `images/<name>.png` of the mod, stretched to w by h; `tint` multiplies its colours (and alpha). 8 bit RGB or RGBA PNG, at most 2048 by 2048, no interlacing. A name that cannot be loaded draws nothing and the log says why. |
| `dcmod.ui.clear(id)` | Removes an item. |

```lua
dcmod.every(0.1, function()
  local car = dcmod.car()
  if not car then return end
  dcmod.ui.rect("bg", 0.40, 0.82, 0.20, 0.12, { 0, 0, 0, 0.55 }, 0.5)
  dcmod.ui.text("kmh", 0.42, 0.83, "Speed " .. math.floor(car.kmh) .. " km/h", 44, { 1, 0.8, 0, 1 }, 0.5)
  dcmod.ui.rect("rpm", 0.42, 0.935, 0.16 * (car.rpm / car.max_rpm), 0.012, { 1, 0.2, 0.1, 1 }, 0.5)
end)
```

The whole example is `tools/modkit/examples/speed-hud`. Checked in the game (Ferrari 458 on Chile): the box, the speed in yellow, the gear and engine speed in white and the red engine speed bar were drawn over the race and followed the car, at 88 frames a second with the upscaler on.
nPictures: a 256 by 256 RGBA PNG with a transparent corner area drew with its transparency, and a second copy with a red half-transparent tint drew tinted next to it, over the race at 89 frames a second; a name with no file drew nothing. The pictures are loaded the first time they are drawn and kept, so change the file and restart to see a new one. Textures come from the ImGui texture system (no Vulkan code of the mod kit), they belong to the overlay and are not filtered by `dcmod.postfx`.

Each call is a path the runtime recognises (`dcmod/ui/...`, `src/runtime_modapi.c`), like `dcmod.log`. The game lower-cases paths, so the library sends a capital letter as `^` and the letter, and any other character outside letters, digits and ` .:=_,-()[]` as `~` and two hex digits, and the runtime turns them back.

### Time of day: `dcmod.time()` and `dcmod.set_time(hour)`

`dcmod.time()` returns the hour of the day of the scene (0 to 24, for example 18.5 is 18:30) and the speed of the clock (`hour, compression`), or `nil` when no race is loaded. `dcmod.set_time(hour)` moves the clock to that hour; the sky, the lights and the shadows follow, and the clock keeps running from there. Values are kept to a thousandth of an hour.

```lua
dcmod.on_ready(function()
  dcmod.after(5, function() dcmod.set_time(3) end)   -- five seconds into the race: night
end)
```

Checked in the game (Ferrari 458 on Chile, started at 18:00): the log read hour 18.00, after `dcmod.set_time(3)` it read 3.00 and stayed there, and the picture went from dusk to a dark night with stars and the car's tail lights on. The same `dcmod/state/env.lua.bin` route as `dcmod.car()` is used, and the request is a `dcmod/env/time/<hour * 1000>` path (`src/runtime_modapi.c`).

### Letting the AI drive: `dcmod.ai_drive(on)`

`dcmod.ai_drive(true)` hands the player's car to the game's AI driver, `dcmod.ai_drive(false)` gives it back, `dcmod.ai_drive()` tells who is driving. It is the game's own property `Actor.GetPlayer().UnderPlayerControl` (the benchmark helper uses it too). Checked in the game (Ferrari 458 on Chile, car coasting under the player's control): after the call `UnderPlayerControl` read `false`, and the car, which had been slowing from 185 to 160 km/h, accelerated again and went on round the lap (progress 0.02 to 0.26 in 11 s). Not checked: handing the car back mid-corner, and the other direction while the player is pressing the pedals.

### Keeping values between runs: `dcmod.store`

```lua
local best = dcmod.store.get("mymod.best_lap", 0)      -- the default says what type comes back
dcmod.store.set("mymod.best_lap", 83.4)
dcmod.store.remove("mymod.best_lap")
```

`dcmod.store.get(name, default)` returns the value kept under `name`, or `default` when there is none. The type of the default decides what comes back: a number gives a number, `true`/`false` gives a boolean, anything else gives the text. `dcmod.store.set(name, value)` keeps a number, a boolean or text (up to 255 characters); `dcmod.store.remove(name)` forgets it. Names use letters, digits, `_`, `.` and `-` (start them with your mod's id so mods do not meet); at most 256 values are kept in all. Everything is in the file `dcmod_store.tsv` in the game's user data folder.

Checked in the game over two runs: the first run read the defaults and wrote a number, a text with `/`, `%` and brackets, a boolean and one value it removed again; the second run read the number back as 1 (and wrote 2), the same text, `true`, and found the removed one gone.

How it works: values are written by a call to a path the runtime recognises (`dcmod/store/set/<name>/<value>`) and read from a Lua chunk the runtime writes (`dcmod/state/store.lua.bin`, which returns every name and value as text), the same way as the car and clock state.

### The cars of the race: `dcmod.cars()`

`dcmod.cars()` returns a list with one entry per car of the race (the player and the AI), or an empty list when no race is loaded:

| Field | Meaning |
|---|---|
| `name` | The vehicle name, for example `ferrari_458_italia` |
| `progress` | How far round the lap the car is, 0 to 1 (the game's `Poslen` property; it wraps to 0 at the line) |
| `player` | `true` for the car the player drives |
| `laps` | Laps completed (`CompletedLaps`) |
| `distance` | Distance along the race (`RaceDistance`, a fraction of a lap, negative before the line) |
| `finish` | Finish position, 0 until the car has finished (`FinishPosition`) |
| `car_collisions`, `world_collisions` | Collisions with cars and with the world so far |
| `wheelie_score` | The accumulated wheelie score |
| `actor` | The game's actor object, for the game's own functions (`Actor.GetVehicleName(actor)`, `actor.UnderPlayerControl`, ...) |

This is all the game's script layer tells about other cars. Looking for every name the game's scripts use on a car's actor found these properties: `AccumulatedWheelieScore`, `ActorName` (`racer_HUMAN8` for the player), `CleanSplitPassedThisFrame`, `CompletedLaps`, `FinishPosition`, `IsFinished`, `IsPlayer`, `Performance`, `Poslen`, `RTTEnabled`, `RaceDistance`, `StartLineCrossed`, `TopSpeedThreshold`, `TotalActorToActorCollisions`, `TotalActorToWorldCollisions` and `UnderPlayerControl`. There is no position, speed or orientation (`position`, `speed`, `velocity`, `rotation` read `nil`). Sort by `laps` plus `progress` for a leaderboard.

`Performance` (1 for every car) can be read and written, and the value stays, but it did not change how fast the AI cars drove: all seven AI cars set to 0.3 in one race and to 2.0 in another covered the same distances after eight seconds. It is probably read when the race is set up. Do not rely on it as a difficulty setting.

Checked in the game (Race mode on Chile, Ferrari 458 with seven AI cars): all eight cars listed with their names, the progress of each changed live and wrapped at the line, and the player flag was set on the right car. The example `tools/modkit/examples/race-board` draws a live leaderboard from it: its order, the player's place (5th of 8) and the lap (1 of 5) matched the game's own display.

### Keyboard and mouse: `dcmod.input()` and `dcmod.key(name)`

`dcmod.input()` returns a table while the game window has the focus, and `nil` while another window has it (a script never sees what the player types elsewhere):

| Field | Meaning |
|---|---|
| `mx`, `my` | The mouse in the game window, 0 to 1 from the left and from the top (outside 0 to 1 when the pointer is outside the window) |
| `left`, `right`, `middle` | Mouse buttons held (`true`/`false`) |
| `keys` | A table with `keys[code] = true` for every key held, by Windows virtual key code (65 is A, 118 is F7) |

`dcmod.key("F7")` tells if a key is held: letters and digits by their character (`"A"`, `"5"`), `"F1"` to `"F12"`, `"SPACE"`, `"ENTER"`, `"ESC"`, `"TAB"`, `"UP"`, `"DOWN"`, `"LEFT"`, `"RIGHT"`, `"SHIFT"`, `"CTRL"`, `"ALT"`, `"BACKSPACE"`, `"DELETE"`, `"HOME"`, `"END"`, or a virtual key number.

```lua
local was = false
dcmod.every(0.1, function()
  local down = dcmod.key("F7")
  if down and not was then dcmod.race_weather({ rain = "Heavy" }) end   -- F7 starts a rainy next race
  was = down
end)
```

Checked in the game (hidden test window with the focus, keys sent with `keybd_event`): holding F7 and A together gave `keys` 65 and 118 and `dcmod.key("F7")` and `dcmod.key("a")` true, releasing them gave an empty table; the pointer position was reported. Not checked: the mouse buttons, the wheel (not reported), the Linux build (always `nil`, the keys come from the Windows API).

How it works: `dcmod/state/input.lua.bin` is a Lua chunk like the car and clock ones (`src/runtime_modapi.c`, `input_state`). The game's own input system is not touched: pressing a key a mod reads still does what the game does with it.

### Panels with buttons and sliders: `dcmod.gui.app`

```lua
local level, on, clicks = 0.5, false, 0
dcmod.gui.app("My app", function(g)
  g:text("clicks " .. clicks)
  if g:button("Click me") then clicks = clicks + 1 end
  on = g:checkbox("A switch", on)
  level = g:slider("Level", level, 0, 1)
end)
```

`dcmod.gui.app(title, fn [, options])` draws a panel over the game and calls `fn(g)` about 15 times a second while it is shown (immediate mode: `fn` describes the panel each time, the values live in your script). F8 shows and hides it (`options.key` for another key, `options.x`, `options.y`, `options.width` for the place as fractions of the screen, `options.shown = true` to start shown). While the panel is shown a small pointer follows the mouse; use the left mouse button.

| Call | Does |
|---|---|
| `g:text(s)` | A line of text |
| `g:button(label)` | A button; returns `true` in the call where it was clicked |
| `g:checkbox(label, value)` | A switch; returns the new value |
| `g:slider(label, value, min, max)` | A slider you drag; returns the new value |

Sizes follow the height of the game window. Several apps can run at once (give each its own key). The panel only reacts while the game window has the focus, like `dcmod.input()`.

Checked in the game (Ferrari 458 on Chile, mouse and keys fed through `DC_INPUT_FILE`, see below): the panel drew with its title, text, button, switch and slider; a click on the button gave `clicks=1`, a click on the switch turned it on, pressing on the slider and dragging moved the value from 0.50 to 0.15 and then 0.65, and the slider and its number followed. Not checked: the real mouse driving the panel (only the keys were checked with the real keyboard), several apps at once, other window sizes.

For tests, `DC_INPUT_FILE=<file>` replaces what `dcmod.input()` reads with the line in that file, without the window needing the focus, for example `mx 0.1 my 0.32 left 1 w 1902 h 1033 keys 118 65` (mouse position 0 to 1, left button, window size, held key codes). The file is read on every call.

The whole example is `tools/modkit/examples/tuning-panel` (the time of day by slider, a speed read-out).

### Weather: `dcmod.race_weather{ rain = ..., weather = ... }`

```lua
dcmod.race_weather({ rain = "Heavy", weather = "Overcast" })   -- every race from now on
dcmod.race_weather({})                                          -- back to the game's own choice
```

`rain` is one of the game's precipitation presets: `Heavy`, `Mid`, `Light`, `VeryLight`, `Wet` (wet road, no rain), `Damp`, `DryToWet`, `WetToDry`, or the preset's full name (`Heavy Precipitation`). `weather` is the sky: `Clear`, `Cloudy`, `Overcast` or `Stormy`. Leave one out to keep the game's choice for it.

The setting applies to races that load after the call, not to the race that is already running (checked: changing the config in a running race does nothing, the weather is built while the race loads). Call it when the mod starts, or from a menu action, and the next race has that weather.

Checked in the game (Ferrari 458 on Chile at 14:00, Time Trial): without the mod a clear dry day; with `dcmod.race_weather({ rain = "Heavy", weather = "Overcast" })` in a mod script the race loaded with heavy rain, a dark overcast sky, a flooded road with reflections and drops on the screen. Not checked: the other presets and weathers one by one, races started from the menus (the test starts the race with the benchmark helper), Linux.

The whole example is `tools/modkit/examples/rainy-night`; with it, a race at 18:00 on Chile loaded in heavy rain under a dark overcast sky.

How it works, for people who extend it: the race config of the game is C++ data, so the script cannot set it (the copy in Lua, `GameConfig.data`, is not read). The script opens `dcmod/env/rain/<name>` and `dcmod/env/weather/<name>`; the runtime keeps the two names and writes them into the config's name strings (with the game's own string assign, `runtime_set_race_config_name` in `src/runtime_benchmark.c`) on every file open, so the config has them whenever a race loads. While the race clock runs and the car is not driven the script also sends the game's `SetPrecipitationFromGameConfig` and `SetInitialPrecipitationState` events, and `StartDrivingPrecipitation` when the car can be driven, the same sequence the benchmark helper uses.

### Post-processing: `dcmod.postfx`

`dcmod.postfx.use(name)` switches on a filter shader that the mod ships (`postfx/<name>.spv`), `dcmod.postfx.param(i, value)` sets the numbers it reads. See [postfx.md](postfx.md).

### Editor support

`docs/modding/lua-defs/dcmod.lua` holds type definitions for the `dcmod` library and every global table of the game (names and kinds of the members; the arguments of the game's functions are not known), in the EmmyLua format that the Lua language server of VS Code and IntelliJ read. Add the folder to the library paths of the editor and `dcmod.car()`, `dcmod.ui.text(...)` and the game's tables complete as you type.

### What a script can use

All the globals the game's own scripts use exist when a mod script runs. [lua-api.md](lua-api.md) lists every global with its members, for example `Event.Listen`, `Event.SendEvent`, `Actor.GetPlayer`, `Actor.SpawnActor`, `GameState.StartGame`, `GUIOptions.Set`, `Rewards`, `Vehicles`, `Tracks`, `Tour`, `LAMS`, `HUD`, `Stats`. It was read from the running game. What each function takes is learned from the game's scripts: `dcmod lua dis` shows how they call them, and `dcmod lua survey` lists the calls.

### Things that go wrong in scripts

- **Globals are locked.** Reading or writing a global that does not exist stops the script with `Attempt to read nil global 'x'. Globals are locked to prevent typo/spelling bugs`. Use `local` for your own variables. The log line is `Mod: error in timer ...`.
- **Timers run from the front end, not during a loading screen.** `dcmod.after` and `dcmod.every` tick in the menus and in a race, and stop while a race loads. Anything that must happen before a race loads has to be set up in advance (`dcmod.race_weather` does this: the runtime applies it while the race loads).
- **Keep listeners.** The value `Event.Listen` returns has to be kept in a variable (`dcmod.on` does); a listener that is thrown away stops being called.
- **Events seen in tests.** `dcmod.on("NewLap", ...)` is checked. In a test that started the race with the benchmark helper, listeners for `RaceState` and `AnimLibPlaySqMsg` were not called (that helper waits for them in its own way), so do not rely on those two without trying them in your own setup.

### Tried and not working

- `TimeManager.SetGameSpeed` (slow motion) exists in the game's script layer but none of the game's own scripts call it. Called from a mod it fails with `bad argument #N (number expected, got no value)` where N is always one more than the number of arguments given (tried 1, 2 and 3 numbers), and as a method (`TimeManager:SetGameSpeed(0.25)`) with `calling 'SetGameSpeed' on bad self (number expected, got table)`. The game clock (`GameState.CurrentGameTime()`) kept running at normal speed throughout. The binding's real signature is not known.
- Setting the weather of a race that is already running, see [Weather](#weather-dcmodrace_weather-rain--weather--).

### Finding out more

A mod script can walk any table and log it, which is how lua-api.md was made:

```lua
for k, v in pairs(Actor) do dcmod.log(k, type(v)) end
```
